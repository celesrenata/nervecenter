# Conservative SHADOW decision policy v1 for NerveShield (Task 1.6)

Adds `backend/mail_security/policy.py`: a pure, deterministic, versioned decision function that derives a `PolicyDisposition` from the *separate* analytical results of earlier tasks (Task 1.4 provenance-aware authentication, the Task 1.5 deterministic `SecurityFinding` list, the Task 1.3 inspection-completeness state, plus optional uncalibrated-model and untrusted-claim placeholders). The fusion is explicit, most-restrictive-first rule logic keyed off the distinct evidence fields — never a thresholded fused legitimacy number — and the six trust axes plus the technical-authentication block stay distinct in the output. The change also makes an additive schema-parity tightening to `AxisScore` in `models.py`, exports the new symbols from `__init__.py`, and adds a decision-table test suite. The diff touches exactly four files, all inside `backend/mail_security/` and `tests/backend/`; nothing is persisted, wired, or networked, and no Task-1.7 work is present.

Watch for: (confirmed) `SAFE_TO_PROCESS` is structurally unreachable in Phase 1 because it requires an `INDEPENDENT` auth `PASS` the header classifier can never emit — this is the intended fail-closed posture, not a bug, but reviewers should know the clean path tops out at `LOW_PRIORITY`. (confirmed) a standalone `PROMPT_INJECTION` finding escalates the *disposition* correctly but does not set the `threat_likelihood` axis, leaving a minor axis/disposition asymmetry.

**Verdict**: APPROVED

## High-level view

The decision is derived separately from the evidence exactly as R-011.1 and design §8.1 require. `decide_policy` sets each of the six axes independently in `_derive_axes` and computes the disposition independently in `_derive_disposition`; neither reads a single collapsed legitimacy scalar, and the public result deliberately exposes no `score`/`legitimacy`/`trust_score` attribute. An axis with no supporting signal stays `NOT_EVALUATED` rather than defaulting to a benign `0.0`, so uncertainty is visible.

The fail-closed gating is sound and layered. A high-severity credential/payment/phishing ask forces `REVIEW` (or `RESTRICTED` when paired with a deceptive link or injection) before auth is ever considered, so a compromised-but-provider-authenticated sender is still reviewed (T-02/T-04). Incomplete inspection is never treated as clean (I-02/T-18). The only clean path yields `LOW_PRIORITY` because `SAFE_TO_PROCESS` demands independent cryptographic verification the phase cannot produce — "clean is not safe" is enforced structurally, not just by convention.

The output is SHADOW-only with empty `action_capabilities` and `human_approval_required` set for every non-clean disposition, and `PolicyDisposition` itself rejects any capability in SHADOW mode, so the no-privilege posture is enforced at two layers. Emergency / prior-approval / internal-privilege claims and any uncalibrated model number are recorded as reason codes and otherwise ignored; a test proves they never change the disposition.

The `AxisScore` tightening is genuine additive schema parity: the JSON `score` object lists `value`, `semantics`, `calibration_id`, `evidence_refs` as required keys, and the model now forbids omitting them (nullability preserved where the schema allows null). Per the commit, `AxisScore` is constructed nowhere in `backend/`, so no 1.4/1.5 call site changed and no prior test assertion moved; the recorded full non-integration run is 5073 passed / 0 failed (5060 baseline + 13 new).

### Disposition derived separately from evidence (R-011.1, design §8.1)

`decide_policy` computes `axes = _derive_axes(evidence)` and `disposition, reasons = _derive_disposition(evidence)` as two independent passes over the same `PolicyEvidence`. The disposition rules key off the *separate* fields — `high_impact_ask`, `deceptive_or_impersonation`, `prompt_injection`, `threat_findings_present`, `inspection_complete`, `auth_unknown`, `has_independent_auth` — and never consult a fused number. There is no collapsed legitimacy scalar anywhere: `PolicyResult` carries `policy`, `axes`, `technical_authentication`, `created_at` and nothing else, and test (g) asserts `not hasattr` for `legitimacy`, `legitimacy_score`, `trust_score`, `score` on both the result and the policy block.

### Fail-closed gating and rule ordering (I-02, T-02, T-04, T-18)

The rules are ordered most-restrictive-first, and the ordering is what makes the compromised-signed-sender case correct:

```
Rule 1  high-impact ask (PAYMENT_FRAUD/PHISHING/SOCIAL_ENGINEERING @ HIGH+)
        -> RESTRICTED if also deceptive/impersonation/injection, else REVIEW
Rule 2  deception/impersonation/malware (or prompt injection) -> REVIEW / RESTRICTED
Rule 3  inspection incomplete -> REVIEW if threat findings present, else INCOMPLETE
Rule 4  any remaining threat-severity finding -> REVIEW
Rule 5  clean + complete -> LOW_PRIORITY (SAFE_TO_PROCESS unreachable)
```

Because Rule 1 fires before any auth is examined, a provider-reported DKIM/SPF/DMARC `PASS` cannot downgrade a credential/payment ask — the `_auth_provider_pass()` + payment/credential test lands on `REVIEW`/`RESTRICTED`, satisfying design §8.1's mandate that a high-severity credential/payment instruction mandates review even when authenticated. Rule 1 also sits ahead of Rule 3, so an incomplete inspection that nonetheless carries a high-impact ask is escalated rather than merely marked `INCOMPLETE` — strictly more restrictive, which is the right direction.

Rule 3 enforces "incomplete is never clean": a capped or failed parse with zero findings becomes `INCOMPLETE`, and the corresponding `threat_likelihood` axis stays `NOT_EVALUATED` rather than resolving to a clean `0.0` (asserted in the missing-content test). `_max_severity_value` returns `None` for a finding-less message so `impact_severity` also stays `NOT_EVALUATED` instead of defaulting low.

### "Clean is not safe" and the unreachable SAFE_TO_PROCESS gate (I-02)

Rule 5 is the carried-forward Task 1.5 discipline made structural. A clean, complete message records `AUTH_PROVENANCE_UNKNOWN` and/or `NO_INDEPENDENT_AUTH_EVIDENCE` plus `CLEAN_BUT_UNASSESSED`, then returns `LOW_PRIORITY`. `SAFE_TO_PROCESS` is only reachable through an independent cryptographic `PASS`, and `_has_independent_pass` checks for `AuthProvenance.INDEPENDENT` + `AuthResult.PASS`, which the Task 1.4 header classifier never produces. The gate is written explicitly and self-documenting rather than silently absent, so the abstention is auditable. The clean-but-unassessed test confirms both the UNKNOWN-auth and the incomplete variants stay out of `SAFE_TO_PROCESS`.

This is correct and desirable, but it means the `SAFE_TO_PROCESS` branch has no live path in Phase 1. Worth an ADR note so a later phase that introduces independent verification wires it deliberately rather than someone reading the gate as dead code.

### No privilege propagation; SHADOW grants nothing (R-011.4, R-012.1, §8.4, T-26)

`claims_emergency` / `claims_prior_approval` / `claims_internal_privilege` only append `UNTRUSTED_AUTHORITY_CLAIM_IGNORED`; the emergency-claim test proves the disposition is byte-identical with and without all three claims set. SHADOW mode returns `action_capabilities=[]` and sets `human_approval_required` for every disposition except `SAFE_TO_PROCESS` (which is unreachable), so in practice every emitted verdict requires human approval and grants no capability. The empty-capabilities invariant is enforced twice — once by the policy constructing `[]`, and again by `PolicyDisposition._shadow_has_no_capabilities` which raises if SHADOW ever carries a capability.

### Uncalibrated numbers cannot drive clean (R-007.2)

`model_benign_estimate` is an optional placeholder; when present it adds `UNCALIBRATED_MODEL_ESTIMATE` and nothing else. No `CALIBRATED_PROBABILITY` is ever emitted — `_raw_score` always stamps `RAW_SCORE` with `calibration_id=None`. The uncalibrated-number test feeds `0.99` and confirms the result is not `SAFE_TO_PROCESS` and the threat axis is not a calibrated probability.

### AxisScore schema-parity tightening (additive)

The JSON `score` object requires `value`, `semantics`, `calibration_id`, `evidence_refs` (confirmed against `schemas/security-assessment.schema.json`). Previously `AxisScore` gave `value`/`calibration_id`/`evidence_refs` permissive defaults, so a payload omitting them validated against the model though the schema rejects it. The edit drops those defaults while preserving nullability where the schema allows null (`value` and `calibration_id` stay `| None`, `evidence_refs` must be supplied but may be `[]`). The `_semantics_consistency` and uniqueness validators are untouched. The commit states `AxisScore` is constructed nowhere in `backend/`, so no 1.4/1.5 call site needed updating and no prior assertion changed — consistent with the recorded 5073-passed run.

### Prompt-injection axis asymmetry

`_derive_axes` builds `threat_findings` from `_DECEPTION_CATEGORIES | _HIGH_IMPACT_ASK_CATEGORIES`, and `PROMPT_INJECTION` is in neither set, so a message whose only threat signal is a prompt-injection finding escalates the disposition (Rule 2 matches `prompt_injection` directly) but leaves `threat_likelihood` at `NOT_EVALUATED`. The disposition outcome is safe and conservative; the asymmetry is only that the axis under-reports a signal the disposition acted on. Either fold `PROMPT_INJECTION` into the threat-axis signal set or document the intentional split.

### Test coverage

The decision table covers every required case: benign SPF failure (a), compromised signed sender with payment+credential ask (b), credential ask with deceptive link (c), missing content / `INSPECTION_INCOMPLETE` (d), junk newsletter → `LOW_PRIORITY` (e), clean-but-unassessed in both UNKNOWN-auth and incomplete variants (f), distinct-axes / no-collapsed-score (g), determinism + stable `policy_version` + injected-clock `created_at` (h), and SHADOW empty-capabilities across three parametrized evidence shapes (i). Two extra cases cover the ignored-claim invariant and the uncalibrated-number invariant. Determinism is checked via `model_dump()` equality across two calls with a fixed clock.

Not tested: a `RESTRICTED` outcome is asserted only as a member of a `{REVIEW, RESTRICTED}` set, never pinned exactly, so the deceptive-link-plus-ask → `RESTRICTED` branch and the injection-plus-deception → `RESTRICTED` branch are not independently nailed down. The prompt-injection-only path (disposition vs. axis asymmetry above) is not asserted. These are coverage gaps, not correctness defects.

### Purity and determinism

`decide_policy` reads time only from the injected `clock` callable; there is no `datetime.now()` or wall-clock access in the module, and no I/O, async, DB, or network call (confirmed by grep). Inputs are frozen dataclasses. The only raise is a `TypeError` guard on a non-`PolicyEvidence` argument.
