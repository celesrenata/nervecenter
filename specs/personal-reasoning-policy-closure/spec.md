## Problem

The personal planes that *collect* are done and green (P0–P4: attention, messages, email, voicemail, calendar, contacts, waiting-on, briefing — 559 tests passing, per [gaps1.md](../../gaps1.md) §2). The engines that *understand* do not exist:

- **No Person/Communication objects, no cross-channel Conversation (§5–§7, §32):** `backend/api/models.py` has a flat VIP `Contact` registry (line 570) and a *per-channel* message-thread `Conversation` keyed by (peer, channel) (line 310); there is no person entity linking iMessage/email/voicemail/calendar sources, no normalized channel-agnostic `Communication`, and no cross-channel conversation model — threads of the same person across channels are unrelated objects today. Grep `Commitment` across `backend/` → zero hits; likewise for a canonical `Person` or `Communication` domain model.
- **No detection (§16–§18):** nothing extracts "I'll send the contract Friday" → `Commitment`, "Can you review this?" → `Request`, "due Thursday" → `Deadline`. `AttentionItem` is only produced from manual ingest/waiting-on/calendar.
- **No follow-up scheduling (§57):** `WaitingOnService.follow_up` (backend/waiting_on/service.py:231) is a one-shot draft helper — there are no `FollowUp` objects, timers, or due-notification paths.
- **No drafts plane (§40, §63):** `email/service.py:254 draft_reply` is a rule-based echo (its own comment: "An LLM-backed drafter can replace this later"). No draft store, no drafts API.
- **No privacy/attention policy (§35, §36, §37, §58, §59, §28–§29):** `context/compiler.py` has no personal/engineering firewall; no sensitivity labels on communications; the PDP decides mutations only, not inference routing; no attention budget, quiet periods, or escalation/adaptive-escalation logic.
- **No personal surface layer (§50–§52, §63–§65):** `/api/search` covers the knowledge plane only; no memory extraction into the entity graph; no Daily Operational State rollup behind `nerve today`; the §63 `/api/personal/*` groups are undocumented deviations; **none** of the 11 §64 personal MCP tools exist (suite asserts exactly 18, `tests/mcp/test_mcp_tools.py:59`); no §65 personal CLI commands (12 command groups in `cli/main.py`).

## Goals

1. G-1.2: A Unified Person model with conservative identity resolution and a normalized cross-channel `Communication`/`Conversation` model, wired into existing ingest paths — so the §62 scenario (same person across email/message/voicemail) yields one person, three communications, one conversation.
2. G-1.1: Deterministic, explainable commitment/request/deadline detection (§16–§18) feeding the attention engine, with model-assisted hooks behind the privacy policy (off by default; deterministic path is the contract).
3. G-1.3: A Follow-Up engine that turns unanswered requests and unfulfilled commitments into due `AttentionItem`s with follow-up/don't-follow-up actions.
4. G-1.4: A drafts plane (store + API) that keeps the rule-based drafter as an honest fallback and routes model-assisted drafting through the policy layer; sending stays human-gated (§13, §41).
5. G-1.5: A documented canonical mapping between the §63 `/api/personal/*` groups and the implemented flat API — no behavior change, no surface growth.
6. G-1.6 + G-1.7: The 11 §64 personal MCP tools (29 total) and the §65 personal CLI commands, each runnable against a seeded local backend.
7. G-1.8: Personal privacy/attention policy enforced in code: personal/engineering context firewall (§35), sensitivity labels (§36), OmniRoute inference-routing policy (§37–§39), attention budget (§58), quiet periods (§59), deadline-driven escalation (§28) and adaptive escalation (§29).
8. G-1.9: Cross-channel communication search (§50), selective memory extraction into the entity graph with provenance (§51), and the Daily Operational State rollup (§52).
9. Every surfaced personal item is auditable per §71 (source, reason, model used, classification, priority calculation, actions performed), and the whole feature is evidenced in `docs/implementation-status.yaml`.

## Scope

**In scope:**
- New backend packages: `backend/communications/` (person, identities, communication, conversation, resolution, detection, search, memory extraction), `backend/followups/`, `backend/drafts/`; extensions to `backend/attention/` (budget/quiet/escalation), `backend/briefing/` (daily operational state), `backend/policy/` (inference-routing decisions), `backend/context/` (firewall partition).
- New endpoint modules (flat prefixes): `people`, `communications`, `conversations`, `commitments`, `requests`, `deadlines`, `followups`, `drafts`, plus an operational-state route on the briefing plane and a personal-scoped search route.
- `mcp/tools_module.py` extension (11 §64 tools) and `cli/` new command modules (§65).
- Tests: `tests/backend/test_communications.py`, `test_detection.py`, `test_followups.py`, `test_drafts.py`, `test_personal_policy.py`, `test_personal_search.py` (names per plan), `tests/mcp/*` updates, CLI smoke tests.
- Docs: §63 mapping table in `docs/nervcenter-spec.md`; workstream entry in `docs/implementation-status.yaml`.

**Out of scope:**
- Real OmniRoute transport (G-3.1) and the grounded `ask` pipeline (G-3.2) — this spec defines the *policy and hook interface* they must satisfy, not the transport.
- The synthetic-lab evaluation corpus (G-3.3) — detection tests in this spec use inline fixtures; the lab owns the regression gate.
- Apple personal surfaces (G-2.1–G-2.5: iPhone/Watch views, complications, widgets, relay email/voicemail/calendar capture) and web personal views — they consume the endpoints built here.
- Persistence of the personal planes beyond the house-style in-memory services (see Assumptions), multi-tenant/person-to-person sharing, auto-sending of any channel (§13: "AI drafts, human sends").

## Constraints

- **Deterministic + explainable (§21):** the default detection/drafting/scoring paths must be deterministic and every produced item must carry a non-empty `why[]`; identical input → identical output.
- **Failure principle (§72):** recall-first for deadlines, appointment changes, financial notices, urgent callbacks, and explicit requests; precision-first for marketing/newsletter/social noise. Tests must assert both directions.
- **Local-first (§70):** personal content defaults to `LOCAL_ONLY` inference routing; remote inference requires an explicit policy (§37). No personal content may leave the local boundary by default.
- **No unauthorized impersonation (§13, §41):** drafts are never auto-sent; the API can create/update/discard drafts but `sent` status is only reachable via the relay send path with explicit per-person/per-category authorization.
- **Conservative identity (§6):** uncertain person matches remain separate until explicitly confirmed/merged; no auto-merge.
- **PDP invariants (house style):** default-deny, explicit-deny precedence, approval bindings can never override an explicit DENY — extended, not weakened, for inference-routing decisions.
- **No surface growth (G-1.5):** keep the flat top-level API shape (`/api/attention`, `/api/messages`, …); new endpoint modules get flat prefixes; the §63 `/api/personal/*` names are mapped, not mirrored.
- **MCP test contract:** `tests/mcp/` asserts the full tool list; the count grows 18 → 29 exactly (11 §64 tools added, nothing removed or renamed).
- **House test gate:** `.venv/bin/python -m pytest tests/ -m "not integration"` green after every task; MCP suite green; each §65 CLI command runs against a seeded local backend.
- **Adaptive escalation (§29) and quiet periods (§59) are local and user-controlled:** preferences persist per user, never inferred remotely.

## Assumptions

- The flat API shape decision (gaps1 G-1.5 option (a)) is confirmed: document the mapping, do not build an `/api/personal/*` alias layer in v0.
- The personal planes stay in-memory singleton services with `reset_*` test hooks, matching the existing P0–P4 house style (`attention`, `waiting_on`, `contacts`, `email`, `voicemail`, `messages`). A persistence adapter is a recorded follow-up, not part of this feature.
- Model-assisted detection/drafting hooks exist as interfaces with an injectable inference client; in v0 the deterministic path is the only *required* path (real OmniRoute transport lands in G-3.1, open question #4 in gaps1).
- The 11 §64 tools map 1:1 onto endpoints built in this feature; `snooze_attention`/`resolve_attention` reuse the existing `/api/attention` action endpoints.
- Sending tools (explicitly excluded from the §64 list) will be separately permissioned through the PDP in a later task; this spec only requires the PDP capability to express that permission (AC-R10, last clause).

## Acceptance Criteria

- AC-R01 *(G-1.2, §5–§7)*: `Person`, `ContactIdentity`, `Communication`, `Conversation` domain models exist in `backend/communications/models.py`. `Communication` carries the §7 shape (`channel` ∈ email|imessage|sms|rcs|voicemail, `direction`, `sender`, `recipients`, `timestamp`, `thread_id`, `content_ref`, `attachments`, `classification`, `sensitivity`, `source`). Re-ingest of an existing identity is an idempotent upsert (no duplicate persons).
- AC-R02 *(G-1.2, §6)*: A resolution service maps relay `peer_identifier`, email From-address, voicemail caller, and contact display names to one canonical `Person`. Uncertain matches (different contact value, same display name) remain separate persons; only an explicit `POST /api/people/{person_id}/merge` (with the merged identity) joins them. pytest ≥ 5 tests incl. the uncertain-match negative path.
- AC-R03 *(G-1.2, §32, §62)*: The §62 cross-channel scenario — Alice's email (10:00), iMessage "Sent you the thing." (10:12), voicemail "Call me when you see it." (13:40) — produces exactly one `Person`, three `Communication`s, one `Conversation`; the conversation's attention item is `CALL ALICE` with reason "direct callback request" and context available from all three channels. Scenario test lives in `tests/backend/test_communications.py`.
- AC-R04 *(G-1.1, §16–§18)*: Deterministic extractors in `backend/communications/detection/` produce `Commitment` (`created_from`, `due`, `confidence`, `status`, `why[]`), `Request`, and `Deadline` objects from ingested `Communication`s. Explicit dates, relative dates ("next week", "tomorrow"), business-hour constraints, and "remind me …" phrasings are extracted. A model-assist hook interface (`InferenceAssist`) exists and is **off by default**; the deterministic path is fully green with it off.
- AC-R05 *(G-1.1, §72)*: `tests/backend/test_detection.py` has ≥ 15 tests covering all §16/§17/§18 examples plus edge cases. Recall-first: every one of the six §16 commitment examples and every §18 deadline example is detected from realistic message text. Precision-first: a labeled noise fixture (marketing, newsletters, social noise) produces zero `Request`/`Commitment`/`Deadline` items (or below a stated false-positive threshold).
- AC-R06 *(G-1.1, §8, §21)*: Each detected item emits its §8 event (`commitment.detected`, `request.detected`, `deadline.detected` + the update/overdue variants) and becomes an `AttentionItem` source via the existing attention service; a deadline's proximity influences the item's priority through the existing explainable `_score`, with the detection's `why[]` visible in the attention item's explanation.
- AC-R07 *(G-1.3, §57)*: `FollowUp` model (`target_kind`, `target_id`, `person_id`, `due_at`, `reason`, `created_from`, `status`) + engine in `backend/followups/`. An outgoing request/commitment with no reply by `due_at` produces a due follow-up `AttentionItem` (the §57 "You asked Sam for the document two days ago. No response yet." shape) with Follow up / Wait / Forget actions. `followup.created`/`followup.triggered`/`followup.completed` events fire; snooze and resolve interactions with a live follow-up are tested; the waiting-on plane's existing `follow-up` behavior is preserved (no regression).
- AC-R08 *(G-1.4, §40–§41, §63)*: `Draft` model (`channel`, `conversation_id`, `communication_ref`, `text`, `basis[]`, `model_used`, `classification`, `status`) with endpoints `GET /api/drafts`, `POST /api/drafts`, `GET/PATCH /api/drafts/{id}`, `POST /api/drafts/{id}/discard`. `status` transitions to `sent` **only** through the relay send path, never via these endpoints. The rule-based email drafter remains the honest fallback; a model-assisted drafter path exists behind the PDP inference check and is exercised with a stub inference client in tests.
- AC-R09 *(G-1.5, §63)*: The flat API shape is kept. `docs/nervcenter-spec.md` gains the canonical §63 mapping table (`/api/personal/people → /api/people`, `/api/personal/communications → /api/communications`, …, `/api/personal/attention → /api/attention` (existing), `/api/personal/briefings → /api/briefing` (existing), `/api/personal/drafts → /api/drafts`). All new endpoint modules are registered and return 200 (empty-list envelope) on a fresh backend; no behavior of existing routes changes.
- AC-R10 *(G-1.6, §64)*: `mcp/tools_module.py::_SPEC` gains exactly the 11 §64 tools — `get_attention`, `get_daily_brief`, `get_person`, `get_conversation`, `search_communications`, `get_commitments`, `get_waiting_on`, `create_followup`, `snooze_attention`, `resolve_attention`, `draft_reply` — for 29 tools total. `tests/mcp/` updated (count, names, per-tool method/path/schema contract). The PDP expresses a distinct sending permission so separately permissioned send tools can be added without touching the read tools.
- AC-R11 *(G-1.7, §65)*: New CLI commands `nerve attention`, `nerve attention snooze <id> <when>`, `nerve today`, `nerve commitments`, `nerve waiting`, `nerve brief`, `nerve people <query>`, `nerve communication search <query>` each run against a seeded local backend: list output shows a ranked table with `why` (for `attention`) via `cli/output.py`, and every command supports `--json` and exit codes 0/2/127 per `cli/main.py` convention.
- AC-R12 *(G-1.8, §35)*: Personal/engineering firewall in the context compiler: personal communications are excluded from engineering `compile_context`/`ask` corpora by default. An explicit relevant relationship (e.g., licensing email ↔ HelloDJ goal, §35 example) grants scoped access to *that* communication only. pytest: a seeded personal message never appears in an engineering compile result; with the explicit link, it appears and only it appears.
- AC-R13 *(G-1.8, §36)*: `Communication.sensitivity` uses the §36 label set (PERSONAL / PRIVATE / FINANCIAL / WORK / PROJECT / LOW-SENSITIVITY) with raw content defaulting to `LOCAL_ONLY`. The label is set at ingest by the deterministic classifier (financial keywords → FINANCIAL, etc.) and is overridable via the communications API. The label drives the inference-routing decision (AC-R14) and is returned by `GET /api/communications/{id}`.
- AC-R14 *(G-1.8, §37–§39, §71)*: Inference-routing policy in `backend/policy/`: an inference request carries data-policy metadata (`privacy`, `contains_personal_communications`, `remote_provider_allowed`) and receives a PDP-style decision (`model_tier` ∈ small-local/medium-local/large-reasoning, `remote_allowed`, `policy_id`, `reason`). Confidential/LOCAL_ONLY content is never routed to a remote tier. PDP test matrix: ≥ 6 cases incl. confidential→local-only (assert `remote_allowed is False`), low-sensitivity→remote-allowed when policy permits, and default-deny when no policy matches.
- AC-R15 *(G-1.8, §58, §59, §28, §29)*: Attention budget: per-day cap on FYI/low-priority items with bundling into the briefing (9 low-priority items → 1 bundled briefing entry); urgent items bypass batching. Quiet periods (sleep, meetings, focus, driving, manual DND) suppress notifications but never remove items from the NOW list (verified by test: item present in `/api/attention/now`, notification flag suppressed). Escalation: a TODAY item with a near deadline is promoted to NOW (§28); adaptive escalation (§29) records a per-person/per-channel preference (e.g., "this person only responds to Watch prompts") and applies it; both are user-controllable and local.
- AC-R16 *(G-1.9, §50, §51)*: Cross-channel search: `GET /api/communications/search` (backing `search_communications`) returns communications, people, and conversations across all channels for the §50 example queries ("who asked me for something this week", "find the voicemail about the prescription"). Memory extraction: durable facts from conversations (appointments, decisions, commitments, project requirements, entity relationships, §51 list) become entities in the knowledge graph with provenance (`source: communication:<id>`); routine conversation produces no entities (negative test).
- AC-R17 *(G-1.9, §52)*: `GET /api/briefing/operational` (Daily Operational State) returns the §52 rollup: open commitments, incoming requests, waiting-ons, upcoming deadlines, pending approvals, today's calendar, active incidents, blocked goals — each section backed by its owning service. `nerve today` (AC-R11) and `get_daily_brief` (AC-R10) consume this route.
- AC-R18 *(§71, §73 evidence)*: Every surfaced personal item exposes auditability fields: `source`, `reason`/`why[]`, `model_used` (`"deterministic"` when no model), `classification`, priority calculation inputs, and actions performed (resolve/snooze history). `docs/implementation-status.yaml` gains a `personal-reasoning-policy-closure` workstream with command + result evidence; final gate: `pytest -m "not integration"` green, MCP suite green at 29 tools, all §65 CLI commands run, §61 + §62 scenario tests green.
